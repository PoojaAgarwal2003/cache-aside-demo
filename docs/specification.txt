5. CACHE CONTRACT: EVENTUAL, INVALIDATE-ONLY
-------------------------------------------

PostgreSQL is the source of truth. Cache only product reads, never the
authoritative stock decision during a purchase.

API writes, committed purchases, and database notifications INVALIDATE cached
products. The listener never refreshes products by reading and writing a new
value. This avoids contradictory "evicted but immediately repopulated" rules.
Only a read path may populate the product cache.

Read response:
{source, responseTimeMs, cacheWriteOutcome, flow, data}
Sources:
  REDIS_CACHE
  REDIS_CACHE_AFTER_WAIT
  DATABASE
  DATABASE_FALLBACK
X-Cache: HIT, MISS, BYPASS respectively.
200 for found; 404 for absent, with the same explanatory envelope.
Use dynamic product IDs in explanations, not hardcoded product:1.

Represent cache lookup and write outcomes with types:
- Lookup: HIT(value), HIT_ABSENT, MISS, UNAVAILABLE, CORRUPT.
- Write: STORED, SKIPPED_UNAVAILABLE, REJECTED_GENERATION,
  REJECTED_LOCK, FAILED.
- Inspect: presence, value, remaining TTL, availability, and error separately.
  Never report Redis unavailable as "key missing" or a successful eviction.

Use JSON DTOs, not directly serialized lazy JPA entities.
Positive TTL: 300 seconds + random 0..60 seconds.
Negative-cache TTL: 30 seconds, represented by a versioned typed envelope.
Use a fixed expiry, never sliding refresh on read hits.
Corrupt/unknown-schema entries become misses with explicit diagnostics and
best-effort guarded removal.

Stale-fill protection:
- Use a process/cache epoch and per-product unpredictable generation tokens.
  Include the epoch in Redis data, lock, and generation key namespaces.
- Initialize a missing generation with SET NX and a fresh random token.
  Never normalize missing generations to a reusable token such as 0.
- Capture the epoch/generation BEFORE reading PostgreSQL.
- A Lua invalidation atomically changes the generation and deletes cached
  positive/negative data. A late reader cannot republish under the old token.
- A Lua fill atomically checks captured generation and, when protection is on,
  current rebuild-lock ownership before storing with TTL.
- Keep generation tokens longer than the maximum data/fill lifetime; an expired
  or missing token rejects an old fill. Bound query/fill deadlines and document
  key cleanup. Inactive generations must not accumulate forever.
- Old epochs expire naturally; clear-all/recovery rotates to a fresh epoch
  instead of blocking Redis with KEYS or indiscriminate FLUSHDB.
- If using SCAN for maintenance, restrict it to this app's old namespaces and
  do not claim SCAN plus DELETE is an atomic global invalidation.

After successful API transaction commit:
- Attempt invalidate through the same helper.
- If invalidation fails, mark local cache readiness BYPASS before returning.
  Report the committed database write accurately; do not return a fake rollback
  or encourage duplicate submission because cache cleanup failed.
- A post-commit invalidation is a fast path. Listener invalidation may repeat
  it harmlessly; duplicate notifications must not republish old values.

Honest consistency claim:
- Generation checks prevent an old in-flight fill from surviving a COMPLETED
  invalidation. They do not eliminate the interval between database commit
  and asynchronous notification processing.
- An already executing read may race a write. Cached reads are not linearizable.
- Notification loss can leave data stale until expiry or recovery invalidation.
- Document TTL from fill, maximum in-flight query duration, and detection lag;
  do not claim a strict commit-to-freshness deadline of exactly 360 seconds.
- After writes quiesce and invalidation completes, subsequent reads must
  converge to the current database value.

6. STAMPEDE CONTROL, NOT AN ABSOLUTE SINGLE-QUERY PROMISE
-------------------------------------------------------

Use Redis SET NX PX with a random owner token for a per-product rebuild lease.
Defaults: lock TTL 5s, waiter deadline 3s, polling interval 50ms.
Release with compare-token-and-delete Lua, never unconditional DEL.

Read sequence:
1. Check cache/readiness; on unavailable, use bounded DB fallback without fill.
2. On miss, attempt the rebuild lock.
3. After acquiring, RECHECK cache before reading the database.
4. Capture valid generation; query DB; publish only if generation, epoch,
   readiness, and owner are still valid.
5. Other callers wait with bounded polling, respecting interruption/deadlines.
6. On timeout, use bounded uncached DB fallback or explicit overload rejection.
   Never let a waiter publish without owning the lease.

Add a bounded DB-fallback bulkhead/concurrency limit with queue/deadline limits.
Cache failure must not create unlimited queued DB work.
Return an explicit 503 when capacity is exhausted; do not claim every request
must succeed during an outage.

When stampede protection is off, retain generation fencing but omit the lease
requirement so the experiment isolates duplicate DB loading, not cache safety.
A lease expiring during a slow load can allow another database query.
Reject the old owner's fill; do not claim one query forever under failures.

7. LISTENER, CIRCUIT BREAKERS, AND RECOVERY
-----------------------------------------

DbChangeListener uses SmartLifecycle with an owned JDBC connection, bounded
notification waits, reconnect backoff, shutdown cleanup, and visible health.
Do not consume a permanently checked-out application-pool connection.

LISTEN/NOTIFY is a best-effort invalidation hint, NOT durable CDC.
Do not claim notifications can be replayed after disconnect.
On known listener disconnection, bypass the cache. On startup/reconnect,
register LISTEN successfully and rotate cache epoch before enabling reads.
Already-started old-epoch fills cannot become visible in the new epoch.
Document unobserved failure/delivery gaps and TTL as the fallback.
Durable outbox or logical-decoding CDC is an explicitly deferred extension,
not something silently approximated by notifications.

Use separate named Resilience4j breakers for:
  product-cache, rate-limit, stock-admission.
They share Redis's physical failure domain but not counters or readiness.
An unrelated rate-limit success must not mark product cache data safe.

Suggested per-breaker defaults:
  timeout/connect-timeout 500ms,
  count-based window 10, minimum calls 5, failure threshold 50%,
  open wait 10s, half-open trial calls 3.
Centralize Redis access so calls cannot accidentally bypass their breaker.

Product-cache readiness is separate from circuit state:
  READY / BYPASS / RECOVERING.
- OPEN bypasses reads/fills.
- HALF_OPEN runs bounded health probes, not trusted cached reads.
- CLOSED alone does not mean READY.
- A serialized recovery coordinator rotates epoch, confirms listener health
  and Redis readiness, then atomically publishes READY.
- Failures keep bypass active and surface a recovery reason.
- Do not perform reentrant cache flushes inside breaker transition callbacks.

Use monotonic clocks for local deadlines/durations.
Await states with a deadline in tests, not "exactly six GETs opens it" or
"the fourth request must hit". Probe/call counts are observables, not promises.
Explicitly report database unavailable rather than inventing cached success
for writes or claiming an outage fallback that did not occur.

8. PURCHASES: FIVE STRATEGIES AND REQUEST IDEMPOTENCY
---------------------------------------------------

Use JdbcTemplate/TransactionTemplate and plain parameterized SQL.
Default strategy: ATOMIC_SQL.

NONE:
  Read stock, check, simulated work, then decrement without a stock predicate.
  Deliberately wrong, demo-only. Do not accidentally protect it with a row
  lock acquired before the check. Use controlled barriers to reproduce the race.

PESSIMISTIC:
  In one transaction, SELECT ... FOR UPDATE, verify stock, perform simulated
  work, decrement, record purchase, commit. Configure lock/statement deadlines.

OPTIMISTIC:
  Read stock/version, perform simulated work, conditional update WHERE id=?
  AND version=? AND stock>=?, retry a conflict in a FRESH bounded attempt.
  Maximum 20 attempts with small bounded jitter.
  Do not reuse a stale entity/snapshot or retry in a rollback-only transaction.
  Exhaustion is GAVE_UP, not OUT_OF_STOCK.

ATOMIC_SQL:
  Do simulated work before the atomic inventory decision, then:
  UPDATE products SET stock = stock - :quantity
  WHERE id = :id AND stock >= :quantity
  RETURNING stock, version;
  The database trigger owns the version/timestamp update.
  Distinguish no product from insufficient stock without misreporting success.
  This is the simple baseline against which extra coordination is measured.

REDIS_ASSISTED (accept legacy query value "redis" as an alias):
  Redis Lua may admit requests using a TTL-bounded advisory stock counter.
  PostgreSQL still commits with the same conditional update as ATOMIC_SQL.
  Redis is an admission optimization, not the source of inventory truth.
  A Redis rejection means ADMISSION_REJECTED, not proof that DB stock is zero.
  No automatic fallback to a different purchase strategy; surface Redis failure.

  Include a random counter epoch and unique reservation IDs. Reserve/release
  scripts must be idempotent per reservation and compensation must verify the
  counter epoch. Never blindly INCRBY a missing, replaced, or expired key.
  Bound reservation metadata TTL and document all Lua return states.

  On known DB rollback, compensate best-effort and record failed compensation.
  On unknown commit outcome, first resolve through the persisted idempotency
  record. Never blindly refund a possibly committed purchase.
  Crashes, missed compensation, external stock edits, and expired counters
  can cause counter drift or false rejections. Show this limitation honestly.
  Provide controlled reconciliation/reset only after the fixture's in-flight
  run has drained; show counter-vs-DB values and unresolved reservations.
  Do not resync stock after every purchase in a way that restores quantities
  still reserved by concurrent buyers. Admin resets/external changes must
  invalidate the advisory epoch or mark it untrusted.

Idempotency is REQUIRED for purchase APIs, including experiments:
- Scope Idempotency-Key by client identity; validate length and character set.
- Persist a canonical fingerprint of productId, quantity, and resolved strategy.
- A reused key with a different fingerprint returns 409 IDEMPOTENCY_CONFLICT.
- Same-key concurrent/retried requests cannot decrement twice.
- Persist the committed purchase result and stock decrement in ONE PostgreSQL
  transaction; enforce uniqueness with a DB constraint.
- Acquire/resolve the DB idempotency claim before creating a Redis reservation.
  Duplicate requests do not reserve stock again.
- Persist stable terminal business outcomes and return them on replay.
  Mark replays explicitly; preserve the original stock result/version.
- Transient failure before commit must not permanently poison the key.
  Bound contention waits and distinguish in-progress/retryable outcomes.
- Simulate "commit succeeded, HTTP response lost": retrying the same key
  returns the existing result. Count unique ledger purchases, not HTTP 200s.
- No real external payment occurs. The fake delay is not a transactionally
  coordinated payment integration or exactly-once delivery guarantee.

Implement one shared ledger/idempotency boundary where possible, not five
independent copies of request deduplication.

Safety invariants for protected strategies under the documented run conditions:
- Committed stock never becomes negative.
- Sum of unique committed sold quantities + final stock = initial stock.
- At most one committed purchase per scoped idempotency key.
- Unsuccessful/replayed requests do not secretly decrement stock.
- Every reported SOLD has a committed ledger row.

Do not require all protected strategies to sell every item under arbitrary
timeouts. Report liveness separately: conflicts, GAVE_UP, admission rejects,
overload, Redis failures, and unsold inventory.
For the small healthy controlled ATOMIC_SQL/PESSIMISTIC fixture, configure
adequate deadlines and assert 10 unique unit sales from 50 buyers/10 units.

9. HTTP CONTRACT AND RATE LIMITING
----------------------------------

Validate IDs, quantities, names, price precision/scale, stock ranges, limits,
timeouts, and strategies. Bound numeric inputs and JSON body sizes.
Do not expose SQL errors, stack traces, or secrets in HTTP responses.
Use consistent error bodies: {code, message, requestId, retryable}.

Product API:
- GET /products/{id}: cache envelope, 200 or 404.
- POST /products: validated create, 201 plus Location.
- PATCH /products/{id}: explicit partial update.
- Keep PUT /products/{id} as a documented partial-update compatibility alias
  if preserving the original Bruno workflow; distinguish absent from invalid
  null fields. Explain this nonstandard compatibility choice.
- DELETE /products/{id}: 204 or 404.
- Return 409 for genuine optimistic update conflicts.

Purchase API:
- POST /products/{id}/purchase?strategy=...
- Body {"quantity":1}; an omitted body defaults to 1, invalid null/zero/negative
  or oversized quantities return 400.
- Require Idempotency-Key, expose X-Purchase-Result and replay metadata.
- 200 SOLD; 409 OUT_OF_STOCK, ADMISSION_REJECTED, GAVE_UP or key conflict;
  404 NOT_FOUND; 503 dependency unavailable, overload or bounded wait failure;
  400 invalid request. Include machine-readable distinctions and retryability.
- Include strategy, meaning, productId, quantity, committed stockLeft/version,
  attempts, requestId, purchaseId where applicable, durationMs, and replayed.
- Response stockLeft is the snapshot at that purchase, not a claim of current
  stock after other buyers have committed.

Rate limiter:
- Redis sorted-set sliding-window log with one atomic Lua decision.
- Use Redis server time and unique members; define the boundary precisely:
  retain accepted timestamps in (now - window, now].
- Default 10 accepted requests per client per 10 seconds.
- Return 429 with Retry-After = ceiling of remaining seconds, minimum 1,
  and X-RateLimit-Limit / X-RateLimit-Remaining.
- Expire state and reject oversized identifiers.
- Demo X-Client-Id is a controlled test identity, NOT authentication.
  Explain why it is not trustworthy for public rate limiting.
- Outage policy is fail-open for the lab, explicitly reported as BYPASSED;
  retain the DB bulkhead. Never invent a remaining quota when Redis is down.
- Apply to public product/purchase routes, not local status/run polling.
  Run distinct-client load scenarios separately from same-client limiter tests.

Debug endpoints, demo-only:
- GET /cache/status: each breaker, product readiness, listener health,
  current epoch, last recovery/error, metrics, and plain-English explanation.
- GET /cache/products/{id}: distinguish absent, present, expired, unavailable.
- DELETE /cache/products/{id}: idempotent invalidation; absent is not a 500.
- DELETE /cache/products: rotate epoch; report "invalidated namespace",
  not a fabricated count of physically deleted keys.

12. AUTOMATED ACCEPTANCE TESTS
------------------------------

Use real PostgreSQL/Redis Testcontainers for transaction, trigger, Lua and
failure tests. Mock-only tests do not demonstrate these guarantees.
Separate fast unit tests, integration tests, and browser tests.
Use isolated test schemas/fixtures, bounded waits, cleanup, and useful failures.
Container/tool unavailability is a reported prerequisite failure, not a pass.

Required automated cases:

A. Startup/migrations
- Clean migration, restart without reseeding/resetting, existing-schema upgrade.
- Trigger increments version on JPA, JDBC and direct SQL changes.
- Rollback emits no committed invalidation notification or purchase ledger row.

B. Cache behavior
- Cold found/absent reads populate, subsequent reads hit with expected payloads.
- TTLs are within configured maximums and decrease; do not require a freshly
  sampled TTL to equal its original whole-second value.
- Corrupt JSON, Redis unavailable and absent keys are distinguishable.
- API update/delete/create invalidates positive/negative cache correctly.
- Direct SQL eventually invalidates; wait for the listener event before
  expecting a miss/new value. Do not require an immediate cache HIT.
- Pause reader after it fetched old DB data, commit writer, complete invalidation,
  then release reader: old fill must be rejected; next read sees current data.
- Repeat with a negative-cache fill racing creation.
- Rotate epoch/recover while a fill is paused: old data never enters new epoch.
- Listener disconnect, missed change, reconnect: old epoch is not trusted.

C. Stampede
- Controlled overlap, healthy dependencies, no expiry/deadline violation:
  a single fixture load occurs and other callers hit/wait.
- Do not assert exactly 19 WAIT and 80 HIT in a general load run.
- Protection disabled: controlled overlap demonstrates duplicate reads.
- Owner stalls beyond lease; another loader proceeds; old owner cannot release
  its successor's lock or publish stale data.
- Wait timeout and DB bulkhead exhaustion terminate with explicit outcomes.
- Unknown write/invalidation outcomes force conservative bypass/recovery.

D. Purchases
- A barrier-controlled NONE race reliably demonstrates overselling.
  Do not depend only on Thread.sleep and hope for an interleaving.
- All four protected strategies satisfy safety/conservation under their
  supported, isolated fixture conditions.
- Healthy ATOMIC_SQL/PESSIMISTIC: 50 distinct buyers, 10 units -> 10 unique
  unit sales and zero stock, with no unexplained failures.
- Optimistic version conflict, external SQL conflict, retry exhaustion.
- Quantities greater than 1 and insufficient remaining stock.
- Same key concurrently and after lost response: one committed decrement.
- Same key/different payload: explicit conflict.
- Redis reserve then known DB rollback: compensation does not double-release.
- Redis key expiry/reset before compensation: no resurrection/inflation.
- Redis unavailable, failed compensation, and unknown DB commit:
  report honest outcomes and reconcile ledger without duplicate purchase.
- Inject process termination before/after commit in an owned test child process;
  on restart, ledger/run reporting distinguishes committed and interrupted work.

E. Rate limits/recovery
- Deterministic clock boundary tests of (now-window, now] semantics.
